secret_ai — état des lieux du code

Revue complète du dépôt Aissociate/secret_ai : télé-réalité simulée par agents IA (« Secret House »). Trois analyses parallèles — base de données & RLS, fonctions Edge, frontend React — synthétisées en un plan de correction priorisé.

Stack React 18 + Vite + Supabase + OpenRouter (GPT-4o) + Kie.ai (Sora 2) Volume ~9 500 lignes front, 12 fonctions Edge, 24 migrations Date 30 août 2026
P0

Plusieurs failles sont exploitables sans aucun compte, avec la seule clé anon extraite du bundle JavaScript : les secrets de chaque agent, les clés d'API OpenRouter/Kie.ai, les messages privés payants et les clés d'API des agents sont tous lisibles publiquement. Le principe même du jeu (deviner le secret) est cassé, et des credentials facturés au projet fuitent. À traiter avant toute mise en production.

P0

La clé API OpenRouter du host est lisible sans authentification

Sans compteRLS USING(true)Credential

host_agent_configs contient openrouter_api_key et ses policies SELECT sont USING (true) pour anon et authenticated. client.ts:409 fait select('*'). Un simple curl avec la clé anon récupère la clé OpenRouter facturée au projet.

CorrectifSupprimer les deux policies SELECT. Déplacer la clé dans Supabase Vault / secret d'Edge Function, ne jamais la faire transiter par PostgREST. Considérer la clé actuelle comme compromise et la faire tourner.
P0

secret_keyword — le secret de chaque agent — est en lecture publique

Sans compteGameplay cassé

Policy "Anon can view agents" USING (true) (20260216204334). agents.secret_keyword est peuplé au lancement, et client.ts:51 fait select('*'). Le principe de l'émission — deviner le secret — est résolu en une requête par n'importe quel spectateur.

CorrectifCréer une vue agents_public (liste blanche de colonnes), révoquer SELECT sur agents, faire pointer fetchAgents/fetchAgent dessus. Remplacer tous les select('*') par des colonnes explicites.

agents.api_key publique → usurpation de n'importe quel agent

Sans compteCredential

agent-api/index.ts:82 authentifie l'agent par .eq("api_key", apiKey), mais cette clé est dans la même table agents exposée. Un attaquant lit toutes les api_key et publie messages, DMs et éliminations au nom de n'importe quel agent.

CorrectifExclure api_key de la vue publique ; stocker un hash SHA-256 plutôt que le clair et comparer côté Edge en service_role.

Élévation de privilèges : tout utilisateur peut se déclarer admin

EscaladeWITH CHECK partiel

Policy "Users can update own profile" (20260217010134) : le WITH CHECK (auth.uid()=id) contraint la ligne, pas la colonne. Un PATCH users?id=eq.moi {"role":"admin"} passe et débloque ~20 policies admin. Même chemin à l'inscription (AuthContext.tsx:90, RegisterPage) où role vient du formulaire.

CorrectifTrigger BEFORE UPDATE forçant NEW.role = OLD.role sauf service_role. Idéalement déplacer role vers auth.users.raw_app_meta_data. Retirer role de l'insert client.

set_user_role_by_email : RPC SECURITY DEFINER ouverte à tous

Sans compteEscalade

20260217003810:15 : aucun REVOKE EXECUTE … FROM PUBLIC, aucune vérification d'appelant, aucun search_path. PostgREST expose POST /rpc/set_user_role_by_email à anon : n'importe qui s'attribue 'admin'.

CorrectifREVOKE EXECUTE … FROM PUBLIC, anon, authenticated + SET search_path + garde service_role, ou supprimer cette fonction de bootstrap.
P0

Les DMs privés sont écrits en visibility='public' — le paywall ne protège rien

Sans compteFraude

agent-api:274 et agent-brain:514 écrivent les DMs en public avec le texte intégral dans payload_json.message. La policy générique retourne le contenu complet ; le masquage est purement cosmétique côté rendu (EventFeed.tsx:257). purchaseDmReveal vend un accès déjà gratuit.

CorrectifÉcrire les DMs en visibility='private_admin', policy de lecture conditionnée à EXISTS(dm_reveals …), exposer l'existence via une vue qui masque payload_json.
P1

Fraude sur les paiements : insertion directe d'un paiement confirmed

FraudePrize pool

Policy "Users can insert own payments" avec WITH CHECK (auth.uid()=user_id) seulement — rien ne contraint status ni amount_usdc. Un user insère {amount:999999, status:'confirmed'} et falsifie la cagnotte. dm_reveals/diary_unlocks acceptent amount:0 → déverrouillages payants gratuits.

CorrectifDurcir le WITH CHECK à status='pending' ; confirmation exclusivement par webhook/service_role ; créer dm_reveals/diary_unlocks via une Edge Function qui vérifie un paiement confirmé du bon montant.
P1

Indices verrouillés & historique d'influence lisibles en anon

hints.hint_text exposé même verrouillé (20260216204513, USING(true)). influence_history — instructions privées des owners et réponses internes — est en anon USING(true) (20260216232736) ; comme les policies se combinent en OR, anon voit plus que authenticated.

CorrectifRevenir à USING (unlocked=true) pour le contenu des hints ; supprimer la policy anon sur influence_history (ou la restreindre à spectator_influence).

Injection de prompt → divulgation du secret

Prompt injectionGameplay

Le prompt d'auto-tick est non borné : coût quadratique

Bombe de coûtsQuick win

auto-tick:709 charge tout l'historique de la saison (aucun .limit()), réinjecté sans .slice() dans le system prompt de chaque agent. Cron toutes les 2 min × 3 agents ≈ 2 160 appels/jour/saison à taille croissante. À J+3 le prompt dépasse la fenêtre de gpt-4o-mini.

Correctif.limit(30) sur la requête + .slice(0,15) et msg.slice(0,150) au mapping (aligné sur agent-brain). Refuser l'appel si systemPrompt.length > 12000. One-liner qui coupe la dérive.
P0

La saison ne progresse jamais et ne se termine jamais

Logique métierJeu figé

Aucun code ne met à jour seasons.current_day, ne passe status='ended', ni ne renseigne winner_agent_id/payouts. Conséquences : les quotas journaliers ne se réinitialisent jamais (saison figée en daily_limit_reached après 20 chats), le prize pool n'est jamais distribué, une seule entrée de journal par heure sur toute la durée.

CorrectifCron advance-season-day (00:00 UTC) qui incrémente le jour et purge les compteurs, + close-season déclenché quand count(alive)=1 ou fin de durée, écrivant vainqueur, statut et payouts.

Race conditions : ticks non idempotents

Concurrence

Ouverture dupliquée (auto-tick:453 lit count=0 puis double appel avant insert, en collision avec le trigger de lancement) ; sélection d'agents concurrente ; trois systèmes de compteurs journaliers divergents (agent-api upsert non atomique, auto-tick compte les events, agent-brain sans limite) ; élimination non transactionnelle.

Correctifpg_advisory_xact_lock en tête d'auto-tick ; contrainte UNIQUE sur l'event d'ouverture ; RPC unique increment_message_count() atomique ; accusation+élimination dans une RPC transactionnelle.
P1

Aucun timeout ni backoff sur les appels LLM / Kie.ai

Robustesse

Aucun AbortSignal.timeout() nulle part. auto-tick chaîne jusqu'à 7 appels LLM séquentiels ; un provider lent fait dépasser la limite wall-clock et tout le tick est perdu (rien n'est persisté avant la fin). Le retry d'agent-brain:359 est sans délai et ne vide pas le body (fuite de connexion, rafale sur 429).

CorrectifUn callLLM unique avec signal: AbortSignal.timeout(20000), res.body?.cancel() avant retry, backoff exponentiel + jitter, respect de Retry-After, et Promise.allSettled borné plutôt qu'en série.

Logique métier
